# Developing

For contributors to this repo: the test suites, the harness's modes, and the interop worker. A user of the package needs none of it; the [README](../README.md) is theirs.

## Testing

```sh
bun install && npm test            # the 15 unit suites: the pure core, the transport and the errors (no server)
npm run test:integration           # 9 of the library's integration suites, interop-py, metrics and limits, on durable-engine serve
```

**The integration suites need an engine build from Synadia (`DE_ENGINE`, a path) and a licence (`DE_LICENCE`, a file; or the engine's licence tool, `DE_LICENCE_TOOL`, makes one for the run).** Without either they skip, saying why; a variable that names no file fails the run. `engine.pin` names the engine version the suites were last run against.

The integration suites spawn a `nats-server` (≥ 2.14, from `PATH`) under the library's account-limits profile (`DE_TEST_PROFILE=ngs|tight|none`, default `ngs`), and one `durable-engine serve` per prefix a test uses, stopped after each test. Every standalone engine they start runs with `DE_LICENCE`, the existing-server mode's too. `DE_ENGINE_LOG=1` echoes the engines' logs, and `DE_SDK_LOG=1` gives a worker without a logger a console one. `DE_TEST_RTT_MS=<ms>` puts the library's delay proxy between every test's connection and the server (the engines stay on the direct URL). Nothing reaches beyond 127.0.0.1 but in the mode below.

**The `limits` suite needs the engine's licence tool (`DE_LICENCE_TOOL`) and its fabric build (`DE_ENGINE_FABRIC`)**, for a licence with low limits and an engine in tenancy mode (`serve --tenancy`); without them its tests skip, saying so.

`npm run check` adds the typecheck, lint and formatting.

### Against an existing server

`DE_NATS_URL` points both suites at a server the run does not own (`test/harness/existing.ts`, `python/tests/existing.py`): no spawn and no account profile, **one prefix and one `durable-engine serve` for the run**, started by the harness on the prefix (it provisions the eight; an account too small for them fails the start with the engine's own message). A test whose engine flags (`ackWaitMs`, `lease: false`, …) differ from the running engine's restarts it with them; `streamMaxBytes` is never applied. After each test, a failed or timed-out one too, the harness stops the workers the test left running, withdraws its workflows' polls (`cancelPoll`), purges what the test changed under the prefix, subject by subject (journal, work, timers, the KV keys, the blobs; never `KV_{P}_TENANTS`, the engine's record of the workflow names), and deletes its runs' blobs by name; at the end, with the engine stopped, it deletes every blob of the run's runs. **It deletes no durable.** The prefix has one pair (`{prefix}~worker`, `{prefix}~timer`; a tenant's `{prefix}~{tenant}~…`), bound once by the run's engine at its first poll and kept for the run: deleting it under the engine's long pull would only make it re-bind. It goes with the prefix's streams at the end (`DE_CLEANUP=delete`). It never deletes a stream during the run or touches anything outside the prefix. An assertion over a store's contents counts the test's own runs only. The leftovers check runs after every test, on the prefix's streams, counting only consumers that were not there before the test. Every wait (the test and hook timeouts, a handle's `result()`, the engine's start) is scaled by a factor from the round trip measured at the start, printed once: 1 up to 20 ms, then 1 + RTT/100 (2.52 at the proxy's 150 ms). **A large value's bytes are waited for too:** at the start the harness also measures the throughput, a 4 MiB `put` and `get` through the run's engine on the tests' own link (`throughput 60.55 MiB/s …`, printed next to the round trip), and every test that moves values over the inline limit adds to its waits its bytes over that throughput, × 2 (`moving(n)` / `budget(ms, n)` in `test/harness/mode.ts`, `existing.moving(n)` in Python), n being the `max_payload`s it moves through `put` and `get` in all, from the harness's tally (`.de-run/<prefix>/blob-bytes.tsv`, a line per test). The round-trip factor scales the sum. The whole `offload` suite, the five large `payload-codec` cases, and Python's two large-signal `test_payload_codec_e2e` cases carry it; on a spawned server it is 0. The tests that need a server or a link of their own are skipped, their titles saying why: TypeScript `network` (the 16 of its 17 that run; the 17th was already skipped), `worker-recovery` "a broken timers stream" (1) and `limits` (2: an engine of its own); Python `test_network` (16, likewise), `test_the_maintenance_pass_and_pumps_survive_a_deleted_timers_stream` (1) and `test_limits` (2).

| Variable         | Meaning                                                                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `DE_NATS_URL`    | the server; switches the mode on                                                                                                              |
| `DE_NATS_CREDS`  | its creds file (the clients, the engine's `--creds`, the interop children's `NATS_CREDS`)                                                     |
| `DE_PREFIX`      | the run's prefix (default a generated `de-<8 hex>`)                                                                                           |
| `DE_ENGINE_URL`  | an engine already serving the prefix, by its `/metrics` address; then none is started, and a test needing other flags or a restart is skipped |
| `DE_CLEANUP`     | `delete` or `keep` the prefix's eight at the end; by default a generated prefix is deleted and a `DE_PREFIX` one kept                         |
| `DE_TEST_RTT_MS` | as before: the delay proxy in front of the server, for the tests **and the engine**                                                           |
| `DE_TENANT`      | the tests run as this tenant of an engine in tenancy mode (`serve --tenancy`)                                                                 |
| `DE_ADMIN_URL`   | where the harness reads the prefix's streams and consumers (default `DE_NATS_URL`); as a tenant, the engine's account                         |
| `DE_ADMIN_CREDS` | its creds file (default `DE_NATS_CREDS` when `DE_ADMIN_URL` is unset)                                                                         |

A generated prefix is only ever the run's, so its eight are deleted at the end unless `DE_CLEANUP=keep` (kept, each reserves its `max_bytes`, 1 GiB by default, and a local server's store fills after a handful of runs). A `DE_PREFIX` is kept unless `DE_CLEANUP=delete`. `DE_INJECT_FAILURE=1` adds the tests that fail on purpose (two in each language, `injected-failure.test.ts` and `test_injected_failure.py`, and in TypeScript a passing one after them), to see that a failed or timed-out test leaves nothing behind. At the end the harness prints the prefix's streams (messages, bytes, consumers) and writes them, the engine's `/metrics` and its log to `.de-run/<prefix>/` (Python: `.de-run/<prefix>-py/`): `leftovers.txt` should show no consumers but the prefix's own durables and no messages the run wrote; `metrics.txt` is the engine's `/metrics` (`de_engine_pull_errors_total`, the acks by outcome); `engine.log` is its log.

Locally, against a server started by hand:

```sh
nats-server -js -a 127.0.0.1 -p 14222 -sd /tmp/de-js &
export DE_NATS_URL=nats://127.0.0.1:14222      # a generated prefix each run, deleted at the end
npm run test:integration                        # 125 passed, 23 skipped, ~69 s
DE_TEST_RTT_MS=150 npm run test:integration     # every round trip 150 ms, the engine's too
(cd python && uv run pytest tests/integration -rs)   # 78 passed, 22 skipped, ~60 s
```

Against a remote server, `DE_TEST_RTT_MS` does not apply (the latency is real, and a byte proxy cannot carry TLS). **Over a WAN the large values take most of the time:** `offload` and `payload-codec` move each one as 128 KiB object-store chunks, one dependent round trip of the engine's each, its bytes across your uplink. **The engine's position matters:** an engine run from a laptop crosses the WAN for every chunk it writes or reads; an engine next to the broker has a short hop, and the suite's bytes cross the WAN once. The throughput probe goes through the run's engine, so the budgets follow whichever it is.

**A prefix an older engine used keeps its per-name durables.** Before `engine.pin` `91ac210` the engine bound `de-worker-<wf>` and `de-timer-<wf>` per workflow name. `91ac210` binds one pair (`de~worker`, `de~timer`) and refuses the pair's bind beside a leftover per-name durable (JetStream 10100; the error names them). Remove them first, for example `nats consumer ls DE_WORK` and `nats consumer rm DE_WORK de-worker-<wf>` (and `DE_TIMERS`, `de-timer-<wf>`).

## The interop worker

`conformance/interop/ts-worker.ts` is the library's, on the thin worker: `greet`, `approve`, `boom` and the parked `echo_signal`, with `DE_PAYLOAD_KEY` (hex) for encryption at rest. It needs a `durable-engine serve` on the same prefix:

```sh
NATS_URL=nats://127.0.0.1:4222 DE_PREFIX=de npx tsx conformance/interop/ts-worker.ts   # prints READY
```

The Python suites drive it (`python/tests/integration/test_interop.py`), and `test/integration/interop-py.test.ts` drives the Python interop worker (`python/conformance/worker.py`) with the TypeScript client, each with and without `DE_PAYLOAD_KEY`. `conformance/interop/ts-client.ts` is the library's TypeScript client for the Python reverse suite.

## How the SDK works with the engine

### What moved to the engine

The worker is the API's loop: one `poll` per concurrency slot; for each item the journal (paged with `load`), the library's `executeRun` with its seams as `append`, `wake` and `child` under the item's lease, `extend` every third of the ack wait, then `done`; every poll names the worker, and `stop()` withdraws its waiting polls (`poll {cancelPoll}`), so a stop takes as long as the items in flight; it returns once every poll has returned, an item one was handed in the instant before handed back (`done retry`), so a process may exit right after it. Stop the worker in a `finally`, as the examples do: a process that exits on an error without `stop()` leaves its polls to the engine for their wait, and an item handed to one waits out its ack wait. A value too large for one request goes up in `put` parts and travels as a ref; a ref the engine hands back, for a value too large for a reply, comes down in `get` parts, its digest checked (`src/engine/blobs.ts`, through the library's own offload code). Everything else the library's worker did is the engine's: the consumers, provisioning, the inbound event, the run lease, the ack matrix, `child-done`, the cascade of a cancel, the forward across continue-as-new, the parked index and the lost-wake repair, the maintenance pass, offload.

So `createWorker` takes `nc`, `workflows`, `prefix`, `dependencies`, `concurrency` (default 16), `pollWaitMs` (default 30 000), `logger`, `metrics` and `payloadCodec`. The library's other options are accepted and ignored, each named for the `serve` flag it became: `ackWaitMs` → `--ack-wait`, `maxWorkMs` → `--max-work`, `lease: false` → `--no-lease`, `leaseTtlMs` → `--lease-ttl`, `streamMaxBytes` → `--stream-max-bytes`, `maintenanceIntervalMs` → `--maintenance-interval`, `reconcileGraceMs` → `--reconcile-grace`, and `offload`'s threshold → `--offload-threshold`; `offload: false` keeps its meaning (nothing goes up in parts, a value too large for a request fails loud). `createClient` takes `nc`, `prefix`, `payloadCodec`, `logger`, `metrics` (`blob.put`, `blob.get`) and `offload: false`.

### Signals and `attempt`

**Every `signal` carries an `id`** (the engine journals a signal when the request arrives, deduplicated by `id`; the engine's `API.md`, "signal"): the caller's (`client.signal(runId, name, data, { id })`, Python `id=`), or a UUID generated by the SDK. It is checked with the same token rule as a `runId` (`assertToken("signal id", …)`, before any request); the engine caps no length, so the SDK sets none. The SDK never retries `signal` itself (only `result()` asks again), so the id is the caller's to pass again: a retry after an `EngineUnavailableError`, a timeout or a restart of the caller's own process passes the id of the first try, and the engine answers `ok` and journals nothing more. The id is looked for in two journals only: the run the request names and the generation current when the request arrives. A signal journaled in any other generation (one that was current at the first try and has continued since) is not recognised, and is journaled again. Two signals with the same name and different ids are two signals. `test/integration/signal-id.test.ts` and `python/tests/integration/test_signal_id.py` prove it.

**`ctx.attempt` is the delivery count** of the current frontier (1 on the first delivery), as the engine's `poll` answers it: every delivery counts, an item handed back between engine instances or bounced by the pair's fetcher too, so it is not a count of failures. Not journaled: a crash resets it.

### Errors

A refusal from the engine is a typed error, one per code of the engine's closed set (the engine's `API.md`, the document shipped with the engine, "Errors"; mirrored as `ENGINE_ERROR_CODES` in `src/engine/errors.ts` and `python/src/synadia_durable/_engine/errors.py`; with `DE_ENGINE_API_MD` (the path of the engine's `API.md`), a unit test in each language fails when the engine's table at `engine.pin` has a code the mirror lacks):

| `code`                    | Error                                                                                      | What the SDK does with it                                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid`                 | `InvalidRequestError` (inside an execution `SerializationError`)                           | never retried; inside an execution the run fails                                                                                                                                                                                            |
| `fenced`                  | `FencedError` (`EngineFencedError`, with `expectLastSeq` and `serverCode`)                 | the pure core's halt                                                                                                                                                                                                                        |
| `expired`                 | `LeaseExpiredError`                                                                        | the worker drops the item; it redelivers                                                                                                                                                                                                    |
| `not_found`               | `RunNotFoundError`                                                                         | raised to the caller                                                                                                                                                                                                                        |
| `too_large`               | `PayloadTooLargeError`                                                                     | deterministic: raised, or the run fails                                                                                                                                                                                                     |
| `blob_gone`               | `BlobMissingError` / `BlobIntegrityError`                                                  | the worker parks the run, loud (`done retry`)                                                                                                                                                                                               |
| `unavailable`, `internal` | `EngineUnavailableError` (also no responders, a timeout)                                   | transient: `result()` asks again, inside an execution `done retry`; `internal` is logged at error                                                                                                                                           |
| `tenant_limit`            | `LimitError` (`code`, `limit`: `bytes`, `runs`, `workflows`, `polls`, `rate`)              | **a refusal, never retried**: a client's call rejects with it; `worker.start()` rejects with it when its first poll is refused (`rate` aside); a refused poll is logged at error naming the limit and polled again after 30 s (`rate`: 1 s) |
| `licence_limit`           | `LimitError` (`limit`: `workflows`, `workers`, `runs`, `runsPerDay`, `tenants`, `expired`) | the same; inside an execution (a `child` at `runs`, an `append` at `bytes`) the item goes back (`done retry`), logged at error                                                                                                              |

A closed connection is `ConnectionClosedError`. An engine older than this SDK's floor (no `withdrawn-remembered` in `info.capabilities`) is `UnsupportedEngineError` (`code` `unsupported`, this SDK's, with `engine`, `commit`, `capabilities`, `missing`), never retried. A code the SDK does not know (an engine newer than it) stays `EngineUnavailableError`, logged at warn. A worker whose polls fail (no engine, a slow link) says `poll failed; retrying` once a minute, with the count of failures since.

**Sizes:** a value of any size the blob store holds; one larger than a request (`request_max`, about `max_payload` − 16 KiB) takes a `put` round trip per part of about 6 MiB on an 8 MiB server. After `result()`, `status()` can read the previous state for a round trip of the worker's.

### Running a worker, in detail

The user's half of running it; the engine's operator has the other.

| Concern                            | What to do                                                                                                              | Mechanism                                                                                                                                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| the connection                     | connect with `withReconnectDefaults({ servers, … })`                                                                    | `@nats-io` gives up after 10 reconnect attempts (~20 s) and closes the connection for good; the helper sets the limit to −1 and never overrides an option you set                                                |
| a connection closed for good       | restart the process; point a readiness probe at `worker.health()`                                                       | a waiting `result()` rejects with `ConnectionClosedError` (the run is unaffected); the worker reports `running: false`, `connectionClosed: true`                                                                 |
| no engine, or a slow link          | nothing                                                                                                                 | `worker.start()` warns `no engine answered info; polling until one does`, and the first answered poll checks the engine's floor; a failing poll says `poll failed; retrying` once a minute with a count          |
| a crash mid-step                   | make a step's effect idempotent, keyed by `ctx.key()`                                                                   | a finished step is journaled and never re-run; a step in flight runs again on the next worker (at-least-once)                                                                                                    |
| a step longer than the ack wait    | nothing, up to the engine's `--max-work` (5 min by default)                                                             | the worker `extend`s the lease every third of the ack wait; past `--max-work` the item redelivers. Raising it is the engine operator's flag                                                                      |
| how soon a dead worker's run moves | the engine's `--ack-wait` (30 s by default)                                                                             | the item redelivers once the lease lapses                                                                                                                                                                        |
| plaintext values in the journal    | `payloadCodec: aesGcmPayloadCodec(key)` on **every** worker and client of the prefix (32 bytes, from your secret store) | it transforms the payload slot only; the engine and the console see a run's shape and never a value. Not retroactive, one-way in practice, and the key's rotation is yours (the engine's protocol specification) |
| who may start, signal or cancel    | the account's authorization (standalone), or your tenant's users ([on the fabric](FABRIC.md#standalone-and-the-fabric)) | every call is a request on `{prefix}.api.v1.<op>`                                                                                                                                                                |
